# Игра через интернет из разных городов

## Почему текущая версия работает только в одной сети

Сейчас каждый экземпляр PySide6-приложения напрямую подключается к Oracle по
параметрам `ORACLE_USER`, `ORACLE_PASSWORD` и `ORACLE_DSN` из `.env`.

Для игры из разных сетей пришлось бы открыть порт Oracle в интернет и передать
другому игроку пароль от базы. Так делать нельзя: это небезопасно, усложняет
настройку роутера и позволяет клиенту обращаться к базе в обход правил игры.

Правильная схема:

```text
Игрок 1 (PySide6) ─┐
                   ├── HTTPS/WebSocket ── игровой сервер ── Oracle
Игрок 2 (PySide6) ─┘
```

Oracle и её пароль доступны только игровому серверу. Игроки знают только публичный
адрес сервера и входят под своими игровыми логинами.

## Рекомендуемый вариант

Разместить на одном удалённом сервере:

- Oracle Database;
- серверное Python-приложение на FastAPI;
- обратный прокси Caddy или Nginx с HTTPS;
- фоновый обработчик игровых таймеров.

PySide6 остаётся настольным клиентом. Вместо прямых вызовов Oracle клиент отправляет
запросы серверу.

Пример адреса:

```text
https://monopoly.example.ru
```

В `.env` игрока останется только:

```env
GAME_SERVER_URL=https://monopoly.example.ru
```

Параметров `ORACLE_USER`, `ORACLE_PASSWORD` и `ORACLE_DSN` на компьютерах игроков
быть не должно.

## Что должен делать игровой сервер

### Авторизация

- регистрация и вход;
- хранение паролей только в виде безопасных хешей;
- выдача короткоживущего access-токена;
- проверка токена перед каждым игровым действием.

Клиент не должен передавать серверу `ID_УЧАСТНИКА` как доказательство личности.
Сервер сам определяет пользователя по токену и проверяет его участие в игре.

### Комнаты

- список доступных комнат;
- создание, подключение и выход;
- удаление комнаты хозяином;
- готовность игроков;
- автоматическая отправка обновлённого списка участников всем клиентам комнаты.

### Игра

- бросок кубика;
- покупка собственности и улучшений;
- аренда;
- аукцион;
- залог, продажа построек и выкуп;
- завершение хода;
- банкротство и определение победителя;
- получение поля, балансов, журнала и статистики.

Все проверки и денежные операции должны выполняться только сервером и Oracle-пакетом.
Клиент отвечает исключительно за отображение и отправку команды пользователя.

## Обновление интерфейса

Для игровых событий лучше использовать WebSocket:

```text
wss://monopoly.example.ru/ws/games/{game_id}
```

Сервер отправляет сообщения:

```json
{
  "type": "game_updated",
  "game_id": 42,
  "revision": 137
}
```

После сообщения клиент получает новое состояние либо сразу принимает готовые данные.
Так изменения комнаты, ставки, движение и передача хода появятся у всех почти
моментально, без постоянного опроса Oracle.

Если WebSocket временно отключился, клиент должен:

1. показать статус «Переподключение»;
2. повторить подключение с увеличивающейся задержкой;
3. после восстановления запросить полное состояние игры;
4. не считать кратковременный обрыв добровольным выходом.

Обычный HTTP polling можно оставить как резервный вариант раз в 5–10 секунд.

## Предлагаемые API-методы

```text
POST   /api/auth/register
POST   /api/auth/login

GET    /api/rooms
POST   /api/rooms
POST   /api/rooms/{id}/join
POST   /api/rooms/{id}/leave
DELETE /api/rooms/{id}
POST   /api/rooms/{id}/ready

GET    /api/games/{id}
POST   /api/games/{id}/roll
POST   /api/games/{id}/buy
POST   /api/games/{id}/decline-purchase
POST   /api/games/{id}/improve
POST   /api/games/{id}/end-turn
POST   /api/games/{id}/auction/bid
POST   /api/games/{id}/debt/resolve
POST   /api/games/{id}/leave

GET    /api/statistics/me
GET    /api/statistics/leaderboard
WS     /ws/games/{id}
```

Каждая изменяющая операция должна принимать уникальный `request_id`. Сервер сохраняет
его и не выполняет команду повторно, если клиент отправил её ещё раз после сетевого
сбоя. Это защищает от двойной покупки, двойной ставки и повторного броска.

## Таймеры

Игровой таймер нельзя оставлять зависимым от открытого клиента. Если все игроки
закроют приложение, ход всё равно должен закончиться.

Рекомендуется отдельная серверная задача, которая раз в секунду:

1. находит активные игры с истёкшим сроком;
2. вызывает `monopoly.check_game_timer`;
3. фиксирует транзакцию;
4. отправляет обновление подключённым клиентам.

Oracle `SYSDATE` остаётся единственным источником времени. Клиентский таймер только
визуально показывает значение, полученное от сервера.

## Защита и сетевые настройки

- наружу открываются только порты `80` и `443`;
- порт Oracle `1521` закрыт от интернета;
- соединение игроков работает только через HTTPS/WSS;
- пароль Oracle хранится только в серверном `.env`;
- `.env` не добавляется в Git;
- для сервера создаётся отдельный Oracle-пользователь с минимальными правами;
- запросы входа и регистрации ограничиваются по частоте;
- сервер проверяет длину названий комнат, сообщений и всех числовых значений;
- регулярно создаётся резервная копия базы.

## Варианты размещения

### Вариант 1 — удалённый сервер

Подходит для постоянной игры:

- арендуется VPS с публичным IP;
- устанавливаются Docker и Docker Compose;
- контейнеры запускают API, Oracle и Caddy;
- домен направляется на IP сервера;
- Caddy автоматически получает TLS-сертификат.

Это рекомендуемый итоговый вариант.

### Вариант 2 — домашний компьютер через VPN

Для быстрой игры с другом без разработки API можно временно использовать Tailscale
или ZeroTier. Оба компьютера окажутся в виртуальной частной сети, а друг укажет
VPN-адрес компьютера с Oracle:

```env
ORACLE_DSN=100.x.x.x:1521/FREEPDB1
```

Недостатки:

- хозяин должен постоянно держать компьютер и Oracle включёнными;
- пароль базы находится у другого игрока;
- клиент по-прежнему подключается к Oracle напрямую;
- это решение подходит только доверенным людям и не должно считаться публичным
  сетевым режимом.

Порт `1521` не нужно и не следует пробрасывать на домашнем роутере.

## Изменения в структуре проекта

Предлагаемая будущая структура:

```text
app/
  main.py                 # PySide6-интерфейс
  api_client.py           # HTTP-запросы
  websocket_client.py     # события комнаты и игры

server/
  main.py                 # FastAPI
  auth.py                 # токены и проверка пользователя
  routes/
    rooms.py
    games.py
    statistics.py
  game_service.py         # вызовы Oracle-пакета
  timer_worker.py

database/
  ...

docker-compose.yml
```

Существующий `GameService` можно превратить в интерфейс с двумя реализациями:

- `OracleGameService` — текущий вариант для локальных тестов;
- `ApiGameService` — сетевой вариант для обычных игроков.

Это позволит не переписывать весь интерфейс сразу.

## План реализации

1. Зафиксировать форматы состояния комнаты, игры, поля, игроков и журнала.
2. Создать FastAPI-сервер и перенести в него прямое подключение к Oracle.
3. Реализовать авторизацию и проверку принадлежности игрока каждой игре.
4. Добавить HTTP API для комнат и игровых команд.
5. Создать `ApiGameService` с теми же методами, которые сейчас использует PySide6.
6. Добавить WebSocket и автоматическое переподключение.
7. Перенести обработку таймеров в отдельную серверную задачу.
8. Добавить тесты двух и более клиентов с задержками и разрывами соединения.
9. Подготовить Docker Compose, HTTPS и резервное копирование.
10. Проверить игру между двумя компьютерами из разных сетей.

## Критерии готовности сетевого режима

- игроки подключаются по одному публичному HTTPS-адресу;
- на компьютерах игроков отсутствуют данные доступа к Oracle;
- состояние обновляется у всех участников без ручного обновления;
- повторный сетевой запрос не выполняет действие дважды;
- таймер работает при закрытых клиентах;
- краткий обрыв сети не делает игрока банкротом;
- после переподключения восстанавливаются комната, игра, баланс и журнал;
- Oracle недоступна напрямую из интернета;
- два клиента из разных сетей успешно проводят игру до определения победителя.
