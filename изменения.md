## 1. Убрать `number_list`, перейдя к одному объекту за действие

Файлы: `database/06_create_types.sql`, `database/07_package_spec.sql`, `database/08_package_body.sql`, `app/db.py`, `app/service.py`, `app/ui.py`, установочные скрипты.

Сейчас объявление:

```sql
CREATE OR REPLACE TYPE number_list AS TABLE OF NUMBER;
/
```

создаёт тип коллекции чисел. Например, `number_list(5, 8, 12)` передаёт три идентификатора владений одним параметром. Это не отдельная таблица с игровыми данными. Конструкция `TABLE(p_ownership_ids)` позволяет использовать переданную коллекцию в SQL-запросе.

Тип используется в:

- `mortgage_properties` — залог нескольких объектов;
- `resolve_debt` — обработка списков залогов и продаж построек.

Предлагается заменить пакетную обработку простыми действиями:

```sql
mortgage_property(p_participant_id, p_ownership_id);
sell_building(p_participant_id, p_ownership_id);
```

Последовательность каждой процедуры:

1. Получить и заблокировать нужное состояние игры.
2. Получить объект.
3. Проверить владельца и допустимость действия.
4. Изменить имущество.
5. Начислить деньги.
6. Записать событие.
7. Проверить остаток долга.

Это позволит убрать коллекции, `TABLE(...)`, проверки размеров списков, подсчёты подходящих объектов и значительную часть `resolve_debt` либо всю эту процедуру.

Удалить только файл типа нельзя: сначала нужно изменить сигнатуры и вызовы, убрать создание коллекций в Python и ссылки на тип в установке и удалении объектов.

Потребуется небольшая правка окна управления долгом: сейчас оно позволяет выбрать несколько объектов одновременно.

**Изменение поведения:** сейчас выбранный набор обрабатывается одной транзакцией. При отдельных действиях каждый объект будет обрабатываться самостоятельно. После покрытия долга дальнейшие продажи и залоги могут стать недоступны. Такой порядок нужно явно закрепить в правилах. Простая замена одного пакетного вызова циклом вызовов Python не сохраняет прежнюю атомарность.

## 2. Сократить дублирующие индексы

Файл: `database/02_create_tables.sql`.

Индекс помогает Oracle находить строки по условиям запроса без просмотра всей таблицы. Например, находить участников или события конкретной игры. Он занимает место и обновляется при изменении индексируемых данных. На маленькой учебной базе выигрыш может быть незаметен.

Для `PRIMARY KEY` и `UNIQUE` Oracle обычно создаёт индексы автоматически, если нет подходящих существующих.

| Индекс | Предложение | Причина |
| --- | --- | --- |
| `IX_УЧ_ИГРА` | Кандидат на удаление | Уже есть индекс `UNIQUE(ID_ИГРЫ, ID_ПОЛЬЗОВАТЕЛЯ)` |
| `IX_ВЛАД_ИГРА` | Кандидат на удаление | Уже есть индекс `UNIQUE(ID_ИГРЫ, ID_КЛЕТКИ)` |
| `IX_АУК_ИГРА` | Кандидат на удаление при сохранении `IX_АУК_АКТИВЕН` | Составной индекс начинается с `ID_ИГРЫ` |
| `IX_АУК_АКТИВЕН` | Оставить | Используется для поиска аукциона по игре и статусу |
| `IX_ЖУРНАЛ_НОВЫЕ` | Оставить | Подходит для получения новых событий игры после последнего ID |
| `IX_ЖУРНАЛ_ИГРА` | Рассмотреть удаление | Текущие запросы журнала преимущественно используют ID действия, а не дату |
| `UQ_УЧ_ИГРА_ОЧ` | Оставить | Обеспечивает уникальную очередь после старта и допускает несколько участников без очереди |

Составной индекс `(ID_ИГРЫ, другое_поле)` может обслуживать поиск по одному первому столбцу `ID_ИГРЫ`. Это не гарантия одинаковой скорости при любых данных, но для данной задачи отдельные индексы на первый столбец выглядят избыточными. Решения об ускорении здесь не подтверждены измерениями или планами выполнения.

### Почему нужен уникальный индекс очереди с `CASE`

В лобби у нескольких участников одной игры очередь равна `NULL`. Обычный:

```sql
UNIQUE (ID_ИГРЫ, ОЧЕРЕДЬ_ХОДА)
```

в Oracle не допускает несколько одинаковых сочетаний вида `(7, NULL)`.

Текущий индекс превращает пару в `(NULL, NULL)`, когда очередь ещё не назначена. Такие строки не попадают в обычный B-tree индекс. После назначения очереди проверяется уникальность пары «игра, номер хода».

Поэтому заменять его обычным составным `UNIQUE` без изменения модели нельзя.

Фраза для защиты: «Индекс запрещает одинаковые номера хода внутри игры, но позволяет нескольким игрокам ожидать назначения очереди».

## 3. Исправить ошибки проверок и расчётов

Основной файл: `database/08_package_body.sql`.

### 3.1. Пустой пароль закрытой комнаты

В `join_game` сравнение сохранённого хэша с `NULL` не даёт `TRUE`, поэтому пустой пароль не вызывает ошибку и позволяет пройти проверку закрытой комнаты.

Добавить явную проверку отсутствия введённого пароля, если у комнаты установлен пароль.

### 3.2. Покупка или улучшение другой клетки

В `buy_property` не проверяется совпадение `p_cell_id` с текущей позицией участника. Аналогичная проблема есть у отказа от покупки и действий с улучшениями.

Для действий, относящихся только к текущей клетке, убрать внешний параметр `p_cell_id` и получать клетку из записи участника. Это одновременно сокращает параметры и устраняет возможность передать другой объект.

### 3.3. Отсутствие проверки полной цветовой группы

В документе для строительства требуется полная незаложенная группа. `build_house` этого не проверяет. Функция `owns_full_color_group` существует, но текущий код её не вызывает.

Если правило сохраняется, использовать эту функцию при строительстве и учитывать возможность улучшения при обработке клетки. Не удалять функцию как ненужную до согласования правила.

### 3.4. `NULL` в проверке владельца

Условие `owner <> p_participant_id` не отклоняет `NULL`. В частности, при строительстве можно передать свободную улицу банка и пройти эту часть проверки.

Проверять `owner IS NULL` явно либо выбирать объект сразу с условием принадлежности нужному участнику. Проверить аналогичные сравнения в остальных действиях.

### 3.5. Причина и доступность банкротства

В `declare_bankruptcy` условие `p_reason NOT IN (...)` не отклоняет `NULL`. При пустой причине проверки добровольного банкротства обходятся.

Добавить явную проверку `NULL`, если параметр сохраняется. Принудительное банкротство сделать внутренней операцией: внешний вызывающий сейчас может передать причину тайм-аута без подтверждения, что тайм-аут произошёл.

### 3.6. Продление времени покрытия долга

`enter_debt_or_bankruptcy` повторно устанавливает `ВРЕМЯ_НАЧАЛА_ХОДА = SYSDATE`, если после продажи или залога долг сохранился. Поэтому каждое частичное погашение запускает срок заново.

Устанавливать время только при первоначальном переходе в состояние покрытия долга. Частичные погашения не должны менять первоначальный срок, если правила не предусматривают продление.

### 3.7. Неверный исторический получатель аренды

В `get_action_log` и `get_game_snapshot` получатель старой оплаты определяется через текущего владельца клетки. После смены владельца история показывает другого человека или теряет получателя.

Простой вариант: при оплате сохранять имя получателя в уже существующем поле `ТЕКСТ_СОБЫТИЯ`, а при выводе использовать сохранённый текст.

### 3.8. Разные суммы продажи в интерфейсе и процедуре

`get_player_properties` вычисляет:

```sql
FLOOR(цена * 0.25 / 2)
```

Фактическая продажа использует:

```sql
FLOOR(CEIL(цена * 0.25) / 2)
```

При цене 110 интерфейс показывает 13, а процедура начисляет 14. Использовать одинаковую формулу во всех местах.

### 3.9. Денежная карта с пустой суммой

В `CHK_КАРТЫ` условие `СУММА_ИЗМЕНЕНИЯ > 0` не запрещает `NULL`: неизвестный результат допускается ограничением `CHECK`.

Для денежных карт явно требовать `СУММА_ИЗМЕНЕНИЯ IS NOT NULL` вместе с положительным значением. Для карт перемещения сумма должна оставаться `NULL`.

## 5. Удалить действительно повторяющиеся проверки

| Место | Предложение | Условие |
| --- | --- | --- |
| `add_action`: проверка существования клетки через `COUNT(*)` | Убрать | Внешний ключ уже проверяет существование клетки |
| `create_game`: проверка существования пользователя | Можно убрать | Если допустимо получать стандартную ошибку внешнего ключа вместо своего сообщения |
| Регистрация: `p_password IS NULL OR LENGTH(p_password) = 0` | Оставить `IS NULL` | В Oracle пустая строка считается `NULL` |
| `sell_buildings`: `p_count <> 1` | Убрать параметр `p_count` | Если всегда продаётся ровно один уровень |
| Проверки активного аукциона при состоянии `ОЖИДАНИЕ_БРОСКА` | Рассмотреть удаление | Сначала упорядочить переходы состояний и скрыть внутренние процедуры |
| Повторная проверка свободной клетки в отказе и запуске аукциона | Проверять один раз | Внутренний запуск выполняется в той же транзакции под нужной блокировкой |
| Простое `CHECK(поле IS NULL OR поле >= 0)` | Можно сократить до `CHECK(поле >= 0)` | Только если `NULL` разрешён |

Не путать поведение `CHECK` с поведением процедурного `IF`: для обязательных значений нужны явные проверки `NULL` или `NOT NULL`.

### Какие проверки сохранить

- Текущий игрок и допустимое состояние хода.
- Принадлежность имущества игроку.
- Принадлежность связанных записей одной игре.
- Достаточность денег для покупки, строительства, выкупа и ставки.
- Наличие или отсутствие залога и построек.
- Допустимые значения статусов и числовых признаков.
- Уникальность пользователей в игре, владений и ставок.

Обычный внешний ключ на участника подтверждает его существование, но не принадлежность нужной игре. Поэтому такую проверку нельзя автоматически считать дублирующей.

## 6. Сделать PL/SQL более линейным

### Назначение очереди

В `start_game` используется `MERGE` с `ROW_NUMBER()` для случайной очереди. Для 2–4 игроков можно заменить это курсорным циклом:

1. Выбрать участников в случайном порядке через `ORDER BY DBMS_RANDOM.VALUE`.
2. Увеличивать счётчик очереди.
3. Обычным `UPDATE` назначать номер и начальные значения.

Это упрощение объяснения, а не ускорение.

### Создание или обновление ставки

В `make_bid` вместо `MERGE` можно использовать `UPDATE`, затем `INSERT`, если `SQL%ROWCOUNT = 0`. Сохранить уникальность ставки и согласованный порядок блокировок.

### Определение победителя

В `finish_or_continue` получить число активных участников и возможного победителя одним запросом:

```sql
SELECT COUNT(*), MIN("ID_УЧАСТНИКА")
INTO v_player_count, v_winner_id
FROM "УЧАСТНИКИ"
WHERE "ID_ИГРЫ" = p_game_id
  AND "КОД_СТАТУСА_УЧАСТНИКА" = 'АКТИВЕН';
```

Если участников один — использовать найденный ID; если ноль — завершить без победителя; иначе продолжить.

### Неиспользуемый код

`kick_participant` и `request_start` есть в теле пакета, но отсутствуют в спецификации и не вызываются остальным кодом. Если соответствующие возможности не нужны, удалить эти процедуры. Если нужны по окончательному заданию — подключить их к нужному сценарию. Справочники сохранить.

### Имена переменных

Заменить короткие `g`, `cur`, `st`, `n`, `mx` на `v_game_id`, `v_current_player_id`, `v_game_status`, `v_player_count`, `v_max_players` и аналогичные понятные имена.

## 7. Упорядочить блокировки

В запросах с соединениями используется `FOR UPDATE` без `OF`. Например, бросок соединяет участника, игру и справочник клеток. В таком случае Oracle блокирует выбранные строки всех участвующих таблиц, включая общие клетки разных партий.

Предлагаемое простое правило: каждое изменение партии сначала блокирует строку этой игры, затем проверяет условия и изменяет остальные данные. Все изменяющие процедуры должны соблюдать одинаковый порядок. Для небольшой игры последовательное выполнение действий внутри одной партии приемлемо.

- Не блокировать неизменяемые справочники; уточнить `FOR UPDATE OF ...` либо разделить запросы.
- Согласовать порядок блокировок игры и аукциона. Сейчас `make_bid` сначала блокирует аукцион, а таймер сначала игру, затем аукцион. Есть предпосылки для взаимной блокировки.
- В `decline_improvement` проверка состояния сейчас выполняется без предварительной блокировки. Проверять состояние под согласованной блокировкой.
- Не удалять `FOR UPDATE` полностью.

## 8. Упростить завершение хода, таймеры и аукционы

### Единый порядок завершения

Сейчас обычное действие выставляет `ЗАВЕРШЕНИЕ_ХОДА`, закрытие аукциона сразу передаёт ход, тайм-аут тоже может передать его напрямую. Документ описывает другой порядок.

Выбрать одно правило завершения и применять его последовательно. Справочник состояний сохраняется. Изменения вызовов Python зависят от выбранного порядка.

### Раннее завершение аукциона

Сейчас аукцион закрывается, когда ответили все участники, даже до истечения срока. Количество участников и ответов считается и в `make_bid`, и в `close_auction`.

Если раннее завершение не обязательно, оставить закрытие только через 30 секунд. Это уменьшит код и приблизит поведение к документу. Если раннее завершение требуется, сохранить его, но избежать повторного подсчёта без необходимости.

### Исключения как обычный ход таймера

Таймер вызывает `close_auction`, затем ловит исключение «Аукцион ещё идёт» как ожидаемый результат.

Проще сначала проверить срок либо сделать внутреннюю процедуру, которая возвращается без ошибки, пока закрывать рано. Не использовать ожидаемое исключение как основной способ проверки времени.

### Выход во время аукциона

`disconnect_player` допускает выход текущего игрока во время аукциона и передаёт ход, оставляя аукцион активным. Инициатор аукциона определяется через текущего игрока, который после этого уже другой.

Согласовать отключение с обработкой аукциона: не допускать смены текущего игрока при сохранении незавершённого аукциона без явно предусмотренного сценария его завершения. Учесть и случай завершения всей игры после выхода.

### Сворачивание окна

В `app/ui.py` метод `changeEvent` при сворачивании вызывает отключение. В активной игре это приводит к банкротству.

Убрать выход из игры при обычном сворачивании окна. Это небольшая, но важная для демонстрации правка Python. Закрытие окна и добровольный выход должны иметь явно согласованные правила.

## 9. Упростить получение состояния для интерфейса

`get_game_snapshot` возвращает шесть курсоров, учитывает версию состояния, отдельно отправляет статические клетки и изменившиеся владения.

Для 12 клеток и 2–4 игроков можно сохранить один вызов снимка, но отказаться от `ВЕРСИЯ_СОСТОЯНИЯ` и условной отправки владений. Возвращать десять владений каждый раз проще, чем сопровождать версию и увеличивать её из `add_action`.

При таком решении согласованно изменить параметры снимка и использование версии в Python. Не удалять поле из таблицы отдельно от зависимого кода.

Получение только новых сообщений и событий по последнему ID можно сохранить: эти данные растут в течение партии.

В `get_game_state` несколько раз запрашиваются сведения одного активного аукциона, используется `KEEP(DENSE_RANK LAST ...)`. При обеспеченной гарантии одного активного аукциона заменить повторные подзапросы одним `LEFT JOIN`. Не скрывать нарушение этой гарантии выбором последнего аукциона.

Упрощение снимка имеет меньший приоритет, чем исправление игровых ошибок. Полная переделка графики не требуется.

## 10. Согласовать описание и реальные правила

Документ был указан как примерный, поэтому расхождения не обязательно означают ошибки: правила могли измениться. До защиты нужно выбрать окончательную версию и привести к ней код и описание.

| Правило | Примерный документ | Текущий код |
| --- | --- | --- |
| Начальные деньги | 1500 каждому | `1200 / число игроков`: 600, 400 или 300 |
| Бонус старта | 200 | 100 |
| Время хода | 5 минут | 2 минуты |
| Аренда коммунальных объектов | Кубик × 4 или × 10 | Кубик × 25 или × 50 |
| Выкуп залога | Половина цены + 10% | 110% полной цены |
| Строительство | Нужна полная группа | Полная группа не проверяется |
| Добровольный залог до броска | Разрешён | Залог разрешён только при долге |
| Добровольный выход | Статус `ПОКИНУЛ` | Статус `БАНКРОТ` |
| Закрытие аукциона | По истечении срока, затем состояние завершения хода | Также при ответах всех; непосредственная передача хода |

В таблице участников остаётся `DEFAULT 1500`, хотя процедуры используют другие суммы. Устранить противоречие.

Уточнить смысл `c_start_balance`: название похоже на начальный баланс одного игрока, но при старте значение делится между участниками. Если это общий фонд партии, переименовать соответственно; если баланс каждого — убрать деление после согласования правил.
