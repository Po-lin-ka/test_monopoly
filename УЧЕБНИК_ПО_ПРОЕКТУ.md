Разбор исходников проекта от 15 сентября 2026 года, обновлённый 18 сентября после исправлений проверки хозяина комнаты, таймеров, чата, ставок и упрощения кода. Правила взяты из кода проекта. ## 2. Где что находится

```text
Кнопка в app/ui.py
  → метод GameService в app/service.py
  → драйвер Oracle через app/db.py
  → публичная подпрограмма monopoly
  → внутренние помощники того же пакета
  → чтение/изменение таблиц
  → COMMIT в Python либо ROLLBACK при ошибке Oracle
  → получение состояния и перерисовка окна
```

Oracle хранит данные и определяет допустимость действий. Python выбирает, что показать, собирает ввод, вызывает БД и анимирует уже вычисленную позицию. ### 2.1. Все 15 таблиц и их связи

| Таблица | Что хранит и с чем связана |
|---|---|
| `СТАТУСЫ_ИГР` | Допустимые состояния партии; на код ссылается `ИГРЫ` |
| `СТАТУСЫ_УЧАСТНИКОВ` | В лобби, активен, банкрот, покинул, исключён; ссылка из `УЧАСТНИКИ` |
| `СТАТУСЫ_АУКЦИОНОВ` | Активен, завершён, не состоялся; ссылка из `АУКЦИОНЫ` |
| `ТИПЫ_ДЕЙСТВИЙ` | Коды и названия событий для `ЖУРНАЛ_ДЕЙСТВИЙ` |
| `СОСТОЯНИЯ_ХОДА` | Этап внутри активной игры; ссылка из `ИГРЫ` |
| `ПОЛЬЗОВАТЕЛИ` | Учётные записи: логин, хэш пароля, дата регистрации |
| `КЛЕТКИ` | Общие для всех партий названия, позиции, цены, типы и цветовые группы |
| `ИГРЫ` | Комната и партия: хозяин-пользователь, текущий участник, победитель, статусы и время |
| `УЧАСТНИКИ` | Пользователь именно в конкретной партии: баланс, позиция, очередь, готовность, тайм-ауты |
| `КАРТЫ_ШАНСА` | Текст и эффект; для перемещения — ссылка на `КЛЕТКИ` |
| `ВЛАДЕНИЯ` | Состояние покупаемой клетки в конкретной партии: владелец-участник, постройки, залог |
| `АУКЦИОНЫ` | Торги по клетке конкретной партии; время, цены, победитель-участник |
| `СТАВКИ` | Ответ одного участника на один аукцион: сумма и время; ноль означает отказ |
| `ЖУРНАЛ_ДЕЙСТВИЙ` | Игровые события партии; участник и клетка могут отсутствовать для системного события |
| `ЧАТ` | Сообщения участников; партия определяется через `УЧАСТНИКИ` |

**Не путать идентификаторы.** Пользователь — постоянная учётная запись. Участник — её участие в одной игре. Клетка — постоянное место на поле. Владение — состояние этой клетки в одной партии. Поэтому в `resolve_debt` передают ID владений, а не ID клеток; в статистику передают ID пользователя, а в `roll_and_move` — ID участника.

Пять справочников статусов/действий нужны по требованиям работы. Внешний ключ разрешает записать только существующий код, а название можно получать через `JOIN`. Сам по себе справочник не разрешает переход между статусами: это проверяет пакет. Оставшийся код `ИСКЛЮЧЕН` допустим в справочнике, хотя отдельной команды исключения в текущем пакете уже нет.

`PRIMARY KEY` идентифицирует строку; `UNIQUE` запрещает дубли; `FOREIGN KEY` проверяет существование связанной строки; `NOT NULL` запрещает отсутствие значения; `CHECK` проверяет условие. Например, пара игра–клетка уникальна во `ВЛАДЕНИЯ`, а заложенный объект не может иметь постройки. Отрицательный баланс разрешён намеренно: так представлен долг. Ссылки на текущего участника и победителя добавлены через `ALTER TABLE` после создания `УЧАСТНИКИ`, потому что между играми и участниками есть взаимные ссылки.

Поле `УЧАСТНИКИ.ПОСЛЕДНЯЯ_СВЯЗЬ` имеет тип `DATE DEFAULT SYSDATE NOT NULL`. Оно хранит время последнего подтверждения присутствия по часам Oracle, а не компьютера игрока. Начальное значение задаётся при вставке, при старте партии `start_game` обновляет его всем активируемым участникам. В лобби время обновляется, но исключение по отсутствию связи применяется только в активной партии. Отдельный индекс не нужен: проверка выбирает до четырёх участников одной игры по уже имеющемуся индексу.

### 2.2. Зачем нужна каждая таблица

На защите удобно объяснять таблицу через вопрос, на который она отвечает. Схема ниже соответствует `database/02_create_tables.sql`.

| Таблица | Зачем она нужна именно в этой игре |
|---|---|
| `СТАТУСЫ_ИГР` | Отвечает на вопрос «на каком этапе находится партия?». Даёт единый набор кодов для ожидания, проверки готовности, активной и завершённой игры. Несколько комнат могут иметь одинаковый статус, поэтому его название хранится один раз в справочнике. |
| `СТАТУСЫ_УЧАСТНИКОВ` | Отвечает на вопрос «в каком состоянии находится игрок в этой партии?». Позволяет различать участника лобби, активного игрока, банкрота и покинувшего игру. Статус партии не заменяет статус участника: игра может продолжаться, когда один игрок уже обанкротился. |
| `СТАТУСЫ_АУКЦИОНОВ` | Описывает результат и состояние отдельных торгов. Нужен отдельно от статуса игры: в одной продолжающейся партии могут быть уже завершённые аукционы. Через код пакет и интерфейс отличают активные торги от завершённых или не состоявшихся. |
| `ТИПЫ_ДЕЙСТВИЙ` | Классифицирует события журнала: бросок, покупка, аренда и другие действия. Позволяет искать события по устойчивому коду и показывать человеку понятное название. Иначе пришлось бы определять смысл события по произвольному тексту. |
| `СОСТОЯНИЯ_ХОДА` | Отвечает на вопрос «что сейчас разрешено сделать текущему игроку?». Разделяет ожидание броска, покупку, улучшение, покрытие долга и другие этапы. Одного статуса «игра активна» недостаточно, чтобы решить, можно ли бросать кубик или покупать клетку. |
| `ПОЛЬЗОВАТЕЛИ` | Хранит постоянную учётную запись для входа и объединяет историю человека за разные партии. Логин и хэш пароля не нужно копировать при каждом вступлении в комнату. Баланса здесь нет, потому что деньги относятся к отдельной партии. |
| `КЛЕТКИ` | Хранит общее описание игрового поля: где находится клетка, как называется, сколько стоит и к какой группе относится. Это позволяет использовать одно поле во всех комнатах. Текущего владельца здесь нет: одна и та же улица в разных партиях принадлежит разным игрокам. |
| `ИГРЫ` | Хранит одну комнату, которая после старта становится партией: её хозяина, настройки, этап, время, текущего игрока и результат. Это центральная запись, по которой отделяются данные разных партий и блокируются одновременные игровые операции. |
| `УЧАСТНИКИ` | Хранит участие конкретного пользователя в конкретной игре. Здесь находятся его деньги, позиция, очередь, готовность, статус, пропуски хода и время последней связи. Без этой таблицы новая партия перезаписывала бы состояние пользователя в предыдущей. |
| `КАРТЫ_ШАНСА` | Хранит возможные случайные события как данные: текст, вид эффекта, сумму либо клетку назначения. Пакет выбирает карту и применяет описанный эффект. Общую колоду не нужно создавать заново для каждой комнаты. |
| `ВЛАДЕНИЯ` | Хранит изменяемое состояние покупаемого объекта внутри партии: владельца, уровень построек и залог. Позволяет отдельно хранить постоянную цену улицы в `КЛЕТКИ` и её состояние в каждой игре. Значение владельца `NULL` означает, что объект принадлежит банку. |
| `АУКЦИОНЫ` | Хранит отдельный эпизод торгов: в какой игре, какая клетка продаётся, когда начались торги, каковы цены, статус и победитель. Одну клетку можно выставлять на торги повторно, поэтому аукцион имеет собственный ID. |
| `СТАВКИ` | Хранит ответ каждого участника на конкретные торги и время ответа. Нужна, чтобы сравнить суммы и понять, все ли уже ответили. Отсутствие строки означает отсутствие ответа, а строка с суммой 0 — явный отказ; для досрочного завершения торгов это разные ситуации. |
| `ЖУРНАЛ_ДЕЙСТВИЙ` | Сохраняет последовательность игровых событий. Текущий баланс показывает только результат, а журнал позволяет объяснить, почему он изменился: аренда, покупка, штраф и т. д. У события есть игра и тип, а участник и клетка указываются только при необходимости. |
| `ЧАТ` | Хранит сообщения игроков и время отправки. Отделён от журнала, потому что сообщение — произвольный текст человека, а игровое событие создаёт пакет при выполнении правил. Автор задаётся участником, поэтому одновременно известна и комната сообщения. |

### 2.3. Почему связи устроены именно так

**«Один ко многим» (1:N)** означает, что одной строке родительской таблицы могут соответствовать несколько строк дочерней. Например, у игры много участников, но каждая строка участника относится к одной игре. При этом «много» допускает и ноль записей: пользователь может ещё не сыграть ни одной партии.

В таблице ниже перечислены все внешние ключи схемы. Стрелка идёт от таблицы, в которой находится внешний ключ, к таблице, на которую он ссылается.

| Связь и поле внешнего ключа | Почему нужна такая связь |
|---|---|
| `ИГРЫ → ПОЛЬЗОВАТЕЛИ`, `ID_ХОСТА` | Один пользователь может создать несколько комнат, у каждой комнаты один хозяин. Ссылка идёт на постоянную учётную запись: при создании записи игры её участники ещё могут быть не созданы. |
| `ИГРЫ → СТАТУСЫ_ИГР`, `КОД_СТАТУСА_ИГРЫ` | Один статус используется многими играми; у игры ровно один текущий статус. Внешний ключ запрещает записать неизвестный код. |
| `ИГРЫ → СОСТОЯНИЯ_ХОДА`, `КОД_СОСТОЯНИЯ_ХОДА` | Один этап хода может одновременно встречаться в разных партиях. В каждой игре хранится один текущий этап, потому что ходит один игрок. До появления хода поле может быть `NULL`. |
| `УЧАСТНИКИ → ИГРЫ`, `ID_ИГРЫ` | Одна игра объединяет несколько участников. Эта ссылка определяет, к какой партии относятся баланс, позиция и готовность игрока. |
| `УЧАСТНИКИ → ПОЛЬЗОВАТЕЛИ`, `ID_ПОЛЬЗОВАТЕЛЯ` | У одного пользователя может быть много участий в разных партиях. Через эту связь собираются его статистика и история, а логин берётся из одной учётной записи. |
| `УЧАСТНИКИ → КЛЕТКИ`, `ID_ПОЗИЦИИ` | Каждый участник находится на одной существующей клетке. На одной клетке могут одновременно стоять несколько игроков, поэтому уникальность позиции участника не нужна. |
| `УЧАСТНИКИ → СТАТУСЫ_УЧАСТНИКОВ`, `КОД_СТАТУСА_УЧАСТНИКА` | Несколько участников могут быть активны или обанкротиться; у каждого хранится один текущий статус из допустимого набора. |
| `ИГРЫ → УЧАСТНИКИ`, `ID_ТЕКУЩЕГО_УЧАСТНИКА` | Выбирает одного участника, который сейчас ходит. Ссылка на пользователя не дала бы напрямую его баланс и позицию именно в этой партии. До начала ходов значение может отсутствовать. |
| `ИГРЫ → УЧАСТНИКИ`, `ID_ПОБЕДИТЕЛЯ` | Фиксирует победившее участие, из которого можно получить и пользователя, и его состояние в партии. Поле допускает `NULL`, пока победителя нет или партия завершилась без него. |
| `КАРТЫ_ШАНСА → КЛЕТКИ`, `ID_ЦЕЛЕВОЙ_КЛЕТКИ` | Несколько карт могут отправлять на одну клетку. Ссылка нужна только картам перемещения; у премии и штрафа она отсутствует. `CHECK` дополнительно требует либо положительную сумму для денежного эффекта, либо клетку для перемещения. |
| `ВЛАДЕНИЯ → ИГРЫ`, `ID_ИГРЫ` | У каждой партии собственный набор состояний объектов. Покупка и залог в одной комнате не меняют имущество в другой. |
| `ВЛАДЕНИЯ → КЛЕТКИ`, `ID_КЛЕТКИ` | Одно описание улицы используется многими партиями. Уникальная пара `(ID_ИГРЫ, ID_КЛЕТКИ)` запрещает создать два состояния одной клетки в одной игре. |
| `ВЛАДЕНИЯ → УЧАСТНИКИ`, `ID_ВЛАДЕЛЬЦА` | Один участник может владеть несколькими объектами, у одного объекта не более одного владельца. Ссылка на участие привязывает имущество к игровому балансу. Для банка используется `NULL`, отдельный пользователь «Банк» не требуется. |
| `АУКЦИОНЫ → ИГРЫ`, `ID_ИГРЫ` | В одной партии может пройти много аукционов. Ссылка отделяет торги разных комнат и позволяет получить текущий аукцион нужной игры. |
| `АУКЦИОНЫ → КЛЕТКИ`, `ID_КЛЕТКИ` | Каждый аукцион продаёт одну клетку, но одна клетка может фигурировать в нескольких аукционах. Вместе с `ID_ИГРЫ` определяется объект, чьё владение изменится после продажи. |
| `АУКЦИОНЫ → УЧАСТНИКИ`, `ID_ПОБЕДИТЕЛЯ` | У торгов не более одного победителя; один участник может выиграть несколько торгов. `NULL` нужен до подведения итогов и при общем отказе. |
| `АУКЦИОНЫ → СТАТУСЫ_АУКЦИОНОВ`, `КОД_СТАТУСА_АУКЦИОНА` | Несколько торгов могут иметь одинаковый статус. Внешний ключ обеспечивает единый набор значений для поиска и отображения. |
| `СТАВКИ → АУКЦИОНЫ`, `ID_АУКЦИОНА` | У одного аукциона несколько ответов участников. По этой связи пакет собирает ставки и определяет результат именно этих торгов. |
| `СТАВКИ → УЧАСТНИКИ`, `ID_УЧАСТНИКА` | Один участник отвечает на разные аукционы. Пара `(ID_АУКЦИОНА, ID_УЧАСТНИКА)` уникальна: для одних торгов у участника одна запись ответа, а не произвольное число строк. |
| `ЖУРНАЛ_ДЕЙСТВИЙ → ИГРЫ`, `ID_ИГРЫ` | У партии много событий. Прямая обязательная ссылка нужна даже системным событиям, у которых нет участника. |
| `ЖУРНАЛ_ДЕЙСТВИЙ → УЧАСТНИКИ`, `ID_УЧАСТНИКА` | Участник может совершить много действий; ссылка позволяет показать автора события. Для событий без конкретного игрока допускается `NULL`. |
| `ЖУРНАЛ_ДЕЙСТВИЙ → КЛЕТКИ`, `ID_КЛЕТКИ` | Одна клетка встречается в разных событиях, например покупке и аренде. Поле необязательное: не каждое действие связано с клеткой. |
| `ЖУРНАЛ_ДЕЙСТВИЙ → ТИПЫ_ДЕЙСТВИЙ`, `КОД_ДЕЙСТВИЯ` | У многих событий один тип. Код нужен для обработки события программой, а справочное название — для отображения человеку. |
| `ЧАТ → УЧАСТНИКИ`, `ID_УЧАСТНИКА` | Один участник отправляет много сообщений. Через него определяются автор и игра, поэтому отдельный `ID_ИГРЫ` в сообщении не нужен: иначе два поля могли бы указывать на разные комнаты. |

**Где здесь «многие ко многим» (M:N).** Пользователи и игры связаны через `УЧАСТНИКИ`: в игре несколько пользователей, пользователь за время работы приложения участвует в разных играх. Уникальность `(ID_ИГРЫ, ID_ПОЛЬЗОВАТЕЛЯ)` запрещает одному аккаунту получить две строки участия в одной партии. Аналогично `СТАВКИ` связывают участников и аукционы, а `ВЛАДЕНИЯ` связывают игры и покупаемые клетки. Эти промежуточные таблицы хранят и свойства самой связи: баланс участия, сумму ответа, постройки объекта.

**Почему взаимные ссылки игр и участников допустимы.** `УЧАСТНИКИ.ID_ИГРЫ` описывает весь состав партии, а `ИГРЫ.ID_ТЕКУЩЕГО_УЧАСТНИКА` и `ID_ПОБЕДИТЕЛЯ` выбирают конкретные роли внутри этого состава. Это разные сведения. Сначала можно создать игру с пустыми текущим участником и победителем, затем добавить участников и заполнить нужные роли. При создании схемы два обратных ключа добавляются через `ALTER TABLE`, когда обе таблицы уже существуют.

**Что обеспечивает внешний ключ, а что — пакет.** Внешний ключ проверяет существование строки, но сам по себе не доказывает, что указанный владелец, текущий игрок или победитель относится к той же игре. Для такой проверки в схеме потребовалась бы составная ссылка с ID игры; здесь согласованность обеспечивается логикой пакета. Аналогично наличие клетки ещё не означает, что её можно купить, а наличие статуса не означает, что в него разрешён любой переход. Ограничение комнаты четырьмя участниками также не следует из связи 1:N: вступление проверяет пакет.

**Почему нет каскадного удаления.** Внешние ключи объявлены без `ON DELETE CASCADE`. База не удаляет автоматически историю, имущество и сообщения при удалении родительской строки. При необходимости очистки пакет должен сначала обработать зависимые записи и ссылки в правильном порядке. Для завершённых партий сохранённые участия позволяют получать историю и статистику.

**Пример для ответа на защите.** «Пользователь Анна участвует в игре №10 и позднее в игре №11. Это одна запись в `ПОЛЬЗОВАТЕЛИ`, но две записи в `УЧАСТНИКИ`, каждая со своим балансом. Описание Павелецкой хранится один раз в `КЛЕТКИ`, а её владельцы и постройки в двух партиях — отдельно во `ВЛАДЕНИЯ`. Поэтому покупка Анной Павелецкой в игре №10 не меняет игру №11. Когда Анна пишет в чат, ID участника сразу определяет, в какую комнату относится сообщение».

## 3. Что такое пакет и зачем он здесь

**Пакет PL/SQL — именованный объект схемы Oracle, который объединяет связанные подпрограммы, константы и другие объявления.** Он компилируется и хранится в БД. Здесь пакет называется `monopoly`, и все игровые команды обращаются к нему: `monopoly.buy_property(...)`.

У него две части: **спецификация** объявляет доступные снаружи элементы, **тело** содержит реализации и закрытые помощники. Можно менять реализацию тела, сохраняя прежний интерфейс вызовов. Это устройство описано в [документации Oracle о пакетах](https://docs.oracle.com/en/database/oracle/oracle-database/19/lnpls/what-is-package.html).

В проекте это **один пакет**, хотя ему соответствуют два файла и две записи `PACKAGE` / `PACKAGE BODY` в `USER_OBJECTS`. `number_list` — отдельный тип, а не второй пакет. Python-каталог `app` тоже называется пакетом в терминологии Python, но к объекту PL/SQL это другое понятие.

Пример из проекта:

```sql
-- В спецификации: клиент знает только такую команду.
procedure buy_property(p_participant_id in number);

-- В теле: реализация получает позицию из БД,
-- проверяет состояние хода, владельца и деньги,
-- списывает цену, назначает владельца и пишет журнал.
```

`calculate_rent`, `add_action`, `process_cell` объявлены только внутри тела. Вызвать `monopoly.calculate_rent(...)` из Python нельзя. Это полезно: клиент не должен отдельно списывать аренду или назначать банкротство, обходя правильный порядок действий. Внешняя команда вызывает нужные помощники сама.

В начале тела часть помощников записана без реализации, с `;` после заголовка. Это **предварительные объявления**: компилятор узнаёт сигнатуру до того, как встретит вызов. Позже в том же теле идёт единственная реализация с `IS ... BEGIN ... END`. Повтор заголовка здесь не означает две процедуры. Например, `process_cell` вызывает `apply_chance`, а та при перемещении снова вызывает `process_cell`.

Для защиты: «Пакет объединяет правила моей игры и предоставляет клиенту понятные команды. Общие действия вынесены во внутренние процедуры, чтобы не копировать код. Спецификация — интерфейс, тело — реализация. Данные партии находятся в таблицах, а не в глобальных переменных пакета».

## 4. Как читать PL/SQL в этом проекте

| Конструкция | Простое объяснение и пример |
|---|---|
| `PROCEDURE` | Выполняет действие. Может передать результат через `OUT`; `RETURN;` без значения просто прекращает выполнение |
| `FUNCTION ... RETURN NUMBER` | Вычисляет и возвращает одно значение, например ID пользователя |
| `IN` | Параметр поступает в подпрограмму; если режим не написан, это тоже `IN` |
| `OUT` | Подпрограмма записывает результат в переданный параметр; так выходят ID новой игры и кубик |
| `DEFAULT` | Значение при пропуске аргумента; явно переданный `NULL` не заменяется значением по умолчанию |
| `IS` | После заголовка начинаются объявления локальных переменных |
| `BEGIN ... END` | Выполняемая часть блока |
| `:=` | Присваивание переменной; в `UPDATE SET` используется `=` |
| `%TYPE` | Тип переменной берётся из типа столбца, например из `ПАРОЛЬ_ХЭШ` |
| `SELECT ... INTO` | Прочитать ровно одну строку в переменные; без строк — `NO_DATA_FOUND`, несколько строк — `TOO_MANY_ROWS` |
| `COUNT(*)` | Посчитать строки; запрос без группировки возвращает одну строку с нулём, даже если совпадений нет |
| `SQL%ROWCOUNT` | Сколько строк затронула последняя SQL-команда; после `UPDATE` ставки определяет, нужен ли `INSERT` |
| `RETURNING ... INTO` | Получить созданный идентификатор прямо из `INSERT` |
| `IF / ELSIF / ELSE` | Выбор ветви алгоритма |
| `FOR r IN (SELECT ...) LOOP` | Перебрать результат запроса; `r` — текущая строка, отдельный `FETCH` не нужен |
| `EXCEPTION` | Обработка ошибки; например, занятый логин получает понятное сообщение |
| `RAISE_APPLICATION_ERROR` | Прекратить действие с кодом и сообщением для клиента |
| `NVL(x, 0)` | Взять ноль, если `x` отсутствует |
| `FLOOR`, `CEIL`, `TRUNC`, `MOD` | Округлить вниз, вверх, отбросить дробь, взять остаток |
| `SYSDATE` | Дата и время сервера Oracle; разность `DATE` выражается в днях, поэтому секунды делят на 86400 |
| `DUAL` | Служебная однострочная таблица для вычисления выражения, например хэша |
| `ROWNUM = 1` | Взять первую строку; сортировку делают во вложенном запросе до ограничения |
| `KEEP (DENSE_RANK LAST ORDER BY ...)` | В `get_game_state` взять значение из последнего события нужного вида по ID |
| `ROW_NUMBER() OVER (...)` | В статистике пронумеровать клетки по частоте посещений и выбрать первую |
| `WITH` | Именованные промежуточные запросы внутри одного запроса статистики, а не новые таблицы |

`NULL` означает отсутствие значения. Сравнение `x <> NULL` не даёт `TRUE`: нужна проверка `IS NULL`. Ветка `IF` исполняется только при `TRUE`, а не при неизвестном значении. Поэтому в проверке хозяина комнаты отдельно написано `p_user_id IS NULL`, а затем выполняется сравнение ID. См. [описание IF в Oracle](https://docs.oracle.com/en/database/oracle/oracle-database/19/lnpls/IF-statement.html).

### 4.1. Курсоры

`SYS_REFCURSOR` — встроенный тип курсорной переменной для передачи результата запроса. `OPEN v_result FOR SELECT ...` открывает выборку, `RETURN v_result` передаёт возможность её читать. Это не готовый список Python. Клиент читает строки и закрывает курсор; у такого типа заранее не закреплён единый набор столбцов. См. [документацию Oracle о курсорных переменных](https://docs.oracle.com/en/database/oracle/oracle-database/19/lnpls/cursor-variables.html).

Пример: `get_player_properties` возвращает несколько строк владений. `Database.cursor_function` читает названия столбцов, приводит их к нижнему регистру и собирает список словарей. `get_game_snapshot` возвращает сразу шесть разных курсоров через `OUT`, поэтому это процедура. Обычные функции чтения таймеры не обрабатывают; snapshot обрабатывает и может изменять БД.

### 4.2. Транзакции и блокировки

Внутри игрового пакета нет `COMMIT` и `ROLLBACK`. Одна публичная команда вместе со всеми её внутренними вызовами исполняется в транзакции соединения. `Database.callproc` фиксирует успешное действие и откатывает его при ошибке Oracle. `GameService.snapshot` делает то же, поскольку проверка таймеров тоже меняет данные. При ручном вызове из SQL Developer фиксацией и откатом управляет вызывающий код.

Для просроченного действия `require_turn_time` выдаёт ошибку до изменения денег, имущества или журнала. Начисление штрафа и переход хода выполняются в следующем snapshot и фиксируются его транзакцией. Поэтому откат отклонённой команды не отменяет штраф: в этой команде его ещё не начисляли.

Пример покупки: списание денег, назначение владельца и запись журнала должны сохраниться вместе. Если не прошла одна из команд, нельзя оставлять только списание. Не следует говорить, что любая ошибка PL/SQL сама всегда откатывает всю транзакцию: в данном приложении это явно обеспечивает Python-обёртка для ошибок Oracle.

`lock_game` выполняет `SELECT ... FOR UPDATE` по одной строке игры. Пока первая транзакция не завершилась, другая изменяющая команда этой же партии ждёт блокировку. Благодаря этому проверка цены/владельца и последующее изменение не разъезжаются между двумя клиентами. Общие клетки поля блокировать не нужно. `lock_user` дополнительно сериализует создание/вход для одной учётной записи. Внутренние помощники обычно рассчитывают, что публичная команда уже взяла нужную блокировку.

Цена простоты: в одной партии даже отправка чата и snapshot могут ждать другую команду этой партии. `FOR UPDATE` здесь без `NOWAIT` и без заданного предельного ожидания. Для маленькой учебной игры такой способ понятен, но не стоит описывать его как максимально производительный.

### 4.3. Зачем `number_list` и можно ли его убрать

```sql
CREATE OR REPLACE TYPE number_list AS TABLE OF NUMBER;
/
```

Это SQL-тип коллекции чисел, а не таблица с постоянно хранящимися строками. `number_list(17, 24)` создаёт значение из двух чисел; `number_list()` — пустую коллекцию. `/` — команда клиента SQL*Plus выполнить накопленный блок, а не часть определения типа на сервере.

`resolve_debt` принимает две такие коллекции: ID владений для залога и ID владений для продажи одного уровня построек. `TABLE(p_mortgage_ids)` позволяет использовать коллекцию как источник строк в SQL; единственный скалярный столбец называется `COLUMN_VALUE`. Через `.COUNT` пакет узнаёт, сколько элементов прислал клиент. Python создаёт объект именно этого SQL-типа через `gettype('NUMBER_LIST').newobject()`.

Пример формы вызова, где числа нужно заменить реальными ID одной партии:

```sql
BEGIN
  monopoly.resolve_debt(
    p_participant_id => 7,
    p_mortgage_ids   => number_list(17, 24),
    p_sale_ids       => number_list(31)
  );
END;
/
```

Сначала проверяются **оба списка целиком**, затем меняются владения и начисляется общая сумма. Порядок элементов не влияет на результат. Дубликат или `NULL` внутри списка не найдёт дополнительной допустимой строки, поэтому сравнение количества строк с `.COUNT` отклонит весь выбор. Незаданная коллекция и пустая коллекция здесь дают нулевое количество; два пустых списка запрещены.

**Просто удалить тип нельзя:** перестанут работать спецификация пакета, `TABLE(...)` и Python-преобразование. Можно заменить его другим способом передачи списков, но CSV потребует разбора строки, JSON — другого контракта и разбора, отдельные вызовы по одному объекту нарушат нынешнюю целостную проверку нескольких объектов. Для сохранения массового выбора этот тип разумно оставить: он проще, чем такие переделки. Он не нарушает требование одного пакета.

## 5. Индексы: что отвечать преподавателю

Индекс — дополнительная структура для поиска строк по ключам. Он занимает место и требует обновлений при изменении данных. Его наличие не обязывает Oracle использовать его: план выбирает оптимизатор. В маленьком справочнике просмотр всей таблицы может быть дешевле.

| Явный индекс | Для чего в этом проекте |
|---|---|
| `UQ_УЧ_ИГРА_ОЧ` | Уникальный индекс по выражению `CASE` для игры и номеру очереди. Запрещает одинаковую назначенную очередь в одной партии. Если очередь отсутствует, оба индексируемых значения становятся `NULL`, такие строки не участвуют в обычном B-tree индексе |
| `IX_ЖУРНАЛ_НОВЫЕ (ID_ИГРЫ, ID_ДЕЙСТВИЯ)` | Соответствует запросу новых событий определённой игры: равенство по игре и диапазон `ID_ДЕЙСТВИЯ > последний_ID` |
| `IX_АУК_АКТИВЕН (ID_ИГРЫ, КОД_СТАТУСА_АУКЦИОНА)` | Помогает искать активные торги одной партии; он обычный, поэтому сам не запрещает два активных аукциона |

**Три — количество явно написанных `CREATE INDEX`, а не общее число индексов.** Oracle также создаёт или использует индексы для `PRIMARY KEY` и `UNIQUE`. Уникальные пары игра–пользователь и игра–клетка уже начинаются с ID игры, поэтому отдельный индекс только на этот первый столбец часто дублирует возможность поиска. Внешний ключ сам по себе не означает автоматическое создание индекса на ссылающемся столбце.

Для этой работы не требуется индексировать каждый столбец и каждый справочник. Первый явный индекс нужен прежде всего для целостности очереди, два других — для повторяющихся запросов. Утверждать конкретное ускорение в разах без плана выполнения и измерения нельзя. Справка: [Oracle, ограничения](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/constraint.html) и [Oracle, CREATE INDEX](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/CREATE-INDEX.html).

## 6. Правила и основные цепочки вызовов

### 6.1. Числа, которые нужно знать

При старте общий фонд 1200 делится на число игроков: 600 для двоих, 400 для троих, 300 для четверых. В лобби в строке участника временно записано 1200; игровой баланс назначает `start_game`.

Поле содержит 12 клеток, 10 из них покупаемые. Кубик один, от 1 до 6. Позиция: `MOD(старая_позиция - 1 + кубик, 12) + 1`. Проход старта приносит 100.

Для улицы ценой `P` и уровнем `L` аренда равна `CEIL(P * (1 + L * 0.25))`; полная незаложенная цветовая группа умножает результат на 2. Уровни 0, 1, 2, 3 обозначают отсутствие построек, один дом, два дома и отель. Строительство стоит `CEIL(P * 0.25)` за уровень; **для строительства вся группа не требуется**. Можно построить один уровень при попадании на свою подходящую улицу.

Коммунальная аренда — кубик × 25, либо кубик × 50, если у владельца две незаложенные коммунальные клетки. У заложенного объекта аренды нет.

Залог даёт `FLOOR(P / 2)`. Продажа одного уровня даёт `FLOOR(CEIL(P * 0.25) / 2)`. Например, при цене 110 постройка стоит 28, продажа уровня даёт 14. Выкуп залога стоит `CEIL(P * 1.10)`, то есть 121 для цены 110 — именно от полной цены, не от полученного залога. Это правило проекта.

Долг хранится как отрицательный баланс. При аренде собственнику сразу начисляется вся сумма, даже если плательщик ушёл в минус. Отдельной таблицы обязательств перед кредитором нет. Частичное погашение с оставшимся имуществом даёт новый срок на покрытие долга. При банкротстве собственность возвращается банку без построек и залога.

Аукцион начинается с половины цены, округлённой вниз. Отказавшийся от покупки текущий игрок не участвует. Остальные отвечают суммой или нулём. Закрытие — после ответов всех оставшихся участников либо через 30 секунд. При одинаковых суммах побеждает более ранняя сохранённая ставка; затем сравнивается ID ставки. Изменение своей ставки обновляет её время.

### 6.2. Состояния хода

| Состояние | Что происходит дальше |
|---|---|
| `ОЖИДАНИЕ_БРОСКА` | Бросок; выкуп залога; API также допускает продажу одного уровня |
| `ОЖИДАНИЕ_ПОКУПКИ` | Купить текущую свободную клетку либо отказаться и открыть аукцион |
| `ОЖИДАНИЕ_УЛУЧШЕНИЯ` | Улучшить текущую свою улицу либо отказаться |
| `ПОКРЫТИЕ_ДОЛГА` | Продать выбранные уровни и/или заложить несколько объектов; иначе возможное банкротство |
| `ПРОВЕДЕНИЕ_АУКЦИОНА` | Остальные игроки отвечают; завершение торгов само передаёт ход |
| `ЗАВЕРШЕНИЕ_ХОДА` | Отдельный вызов `end_turn` передаёт ход, если игра продолжается |

### 6.3. Проследить одно действие от начала до конца

```text
Создание: create_game → lock_user → ИГРЫ + УЧАСТНИКИ
Вход: join_game → lock_user → lock_game → УЧАСТНИКИ
Готовность: set_ready → lock_participant_game → add_action
Старт через опрос: get_game_snapshot → check_game_timer → start_game

Бросок: roll_and_move → require_current_player → add_action → process_cell
Чужая клетка: process_cell → pay_rent → calculate_rent → enter_debt_or_bankruptcy
Шанс: process_cell → apply_chance → [деньги или process_cell для новой клетки]
Покупка: buy_property → require_current_player → изменение денег/владения → add_action
Отказ: decline_purchase → start_auction
Торги: make_bid → lock_game → close_auction → advance_to_next_player
Долг: resolve_debt → process_properties → add_action → enter_debt_or_bankruptcy
Банкротство: declare_bankruptcy → return_properties_to_bank → finish_or_continue
Финиш: finish_or_continue → finish_game (если осталось не больше одного активного)
```

`enter_debt_or_bankruptcy` при отсутствии доступного имущества вызывает `declare_bankruptcy`. Если долг закрыт, ставит `ЗАВЕРШЕНИЕ_ХОДА`; если остался и имущество есть, ставит `ПОКРЫТИЕ_ДОЛГА`. Смена этапа и смена текущего игрока — разные действия.

### 7.55. `heartbeat` — публичная процедура

Исходник: [тело пакета, строка 2496](database/08_package_body.sql#L2496).

```sql
procedure heartbeat(p_participant_id number);
```

`p_participant_id IN NUMBER` — ID участника, от имени которого клиент подтверждает присутствие. Результата и выходных параметров нет. Клиент передаёт только собственный ID; как и остальные команды учебного проекта, процедура доверяет переданному ID при общей учётной записи Oracle. Это не отдельная система аутентификации.

**Локальные данные:** `v_game_id NUMBER` — партия; `v_status VARCHAR2(40)` — её статус; `v_connected NUMBER` — число активных с неистёкшим сроком; `v_now DATE` — время Oracle, зафиксированное после получения блокировки.

**Алгоритм:** через `lock_participant_game` блокирует строку игры. В активной партии считает активных игроков с `ПОСЛЕДНЯЯ_СВЯЗЬ > v_now - c_disconnect_seconds / 86400`. Если таких нет, сначала вызывает `finish_game` без победителя: иначе последовательное исключение всех могло бы ошибочно объявить последнего победителем. Затем для каждого просроченного активного участника вызывает `disconnect_player`. Когда остаётся один действительно присутствующий игрок, существующая цепочка `disconnect_player → finish_or_continue → finish_game` присуждает ему победу. При наличии нескольких оставшихся игра продолжается, а ход и аукцион обрабатываются существующими правилами выхода.

После проверки обновляет время **только переданного участника**, если его статус `В_ЛОББИ`, `АКТИВЕН` или `БАНКРОТ`. Проверка выполняется до обновления: уже просроченный активный игрок не может восстановить участие поздним запросом. `ПОКИНУЛ` не меняется обратно на `АКТИВЕН`. При одновременном отсутствии всех игра уже завершена без победителя; последующее отключение меняет статусы, а владения сохраняются как состояние завершённой партии.

**Таблицы:** `ИГРЫ`, `УЧАСТНИКИ`; через помощников также владения, аукционы и журнал. **Вызывает:** `lock_participant_game`, `finish_game`, `disconnect_player`. **Кто вызывает:** `get_game_snapshot` автоматически; `GameService.heartbeat` доступен для отдельного подтверждения. **Ошибки:** собственных кодов нет; передаёт ошибки помощников и SQL. `COMMIT` внутри нет: изменение времени, исключения и полученный снимок относятся к одной транзакции, которую фиксирует Python.

Проверка выполняется при запросах клиентов, отдельного `DBMS_SCHEDULER` нет. Поэтому при работающем сопернике результат появляется на первом успешном опросе после 60 секунд; при стандартном интервале это обычно ещё до двух секунд ожидания. Если отключены все или сама база недоступна, проверка произойдёт после следующего успешного запроса. Это отдельный срок от двухминутного таймера хода и штрафа за пропуск.

## 8. Как Python вызывает PL/SQL

Эта часть нужна, чтобы объяснить границу ответственности. Правила из раздела 7 повторно в Python не реализуются. `self` в методах — текущий объект; это не аргумент, передаваемый в Oracle. Результат обычного метода без `return` — `None`.

### 8.1. Каждый метод `Database` из `app/db.py`

| Метод | Принимает, как устроен, что отдаёт |
|---|---|
| `__init__()` | Инициализирует соединение через `reconnect()` |
| `reconnect()` | Закрывает прежнее соединение, создаёт новое с `tcp_connect_timeout` и без повторов подключения драйвером, задаёт `call_timeout`; ошибку открытия преобразует в `ConnectionLost` |
| `safe_close(resource)` | Статический метод; закрывает соединение или курсор, подавляя вторичную ошибку Oracle при закрытии |
| `close()` | Безопасно закрывает соединение и устанавливает `connection = None`; повторный вызов допустим |
| `rollback_safely()` | Пытается откатить транзакцию; ошибка отката не заслоняет исходную ошибку команды |
| `is_healthy()` | Локально проверяет наличие и работоспособность соединения; возвращает `bool`, сетевого запроса не выполняет |
| `error(exc)` | По состоянию соединения, признаку `isrecoverable` и коду ошибки выбирает `ConnectionLost` или `DatabaseError`; сохраняет исходный текст |
| `cursor()` | Контекстный менеджер: проверяет соединение, создаёт курсор, отдаёт через `yield`; ошибки Oracle преобразует после безопасного отката; курсор закрывает в `finally`. Охватывает также прямые запросы сервиса |
| `callproc(name, params=None)` | Вызывает процедуру, фиксирует транзакцию, возвращает список параметров с OUT. Обрабатывает также ошибку COMMIT. Никогда не повторяет команду |
| `callfunc(name, return_type, params=None)` | Возвращает результат функции через защищённый курсор; фиксацию не делает |
| `cursor_function(name, params=None)` | Читает возвращённый REF CURSOR в список словарей, гарантирует безопасное освобождение курсора |
| `number_list(ids)` | Создаёт Oracle `NUMBER_LIST`, добавляет целочисленные ID; ошибки драйвера проходят через общий обработчик |
| `message(exc)` | Извлекает исходный текст исключения, в том числе если список `args` пуст |

`DatabaseError` наследует `RuntimeError`; `ConnectionLost` наследует `DatabaseError` и отдельно обозначает обрыв или неопределённый результат команды. Ошибка правил игры остаётся обычной `DatabaseError`. Первоначальная ошибка доступна через `__cause__`; неудачные `rollback` и `close` её не заменяют.

`call_timeout` ограничивает **один обмен с Oracle**, а не весь многошаговый запрос; `tcp_connect_timeout` ограничивает установление TCP-соединения. Локальный `is_healthy()` не заменяет сетевую проверку. Эти различия описаны в [документации драйвера](https://python-oracledb.readthedocs.io/en/v4.0.0/api_manual/connection.html). Если ответ на COMMIT потерялся, операция могла уже выполниться. Поэтому после переподключения клиент сверяет состояние и не повторяет автоматически броски, платежи, ставки или чат.

Большинство методов — однострочные обёртки: аргументы в списке идут в том же порядке, что в спецификации пакета. `create_game`, `roll`, `snapshot` длиннее из-за выходных параметров. Ошибки правил возникают в Oracle и доходят до интерфейса через `DatabaseError`.

`GameService.snapshot` получает шесть выходных курсоров и фиксирует транзакцию только после чтения результатов. Ошибки запроса и фиксации преобразуются через `Database.error`; откат выполняется безопасно. В `finally` все созданные курсоры освобождаются через `safe_close`, поэтому ошибка очистки не скрывает причину обрыва. Отдельный `heartbeat` перед snapshot не нужен: присутствие проверяется внутри PL/SQL-процедуры.

### 8.3. Фоновый снимок и настройки

`SnapshotThread.__init__(participant_id, last_action_id, last_message_id, parent=None)` сохраняет три аргумента запроса в кортеже и инициализирует `QThread`. Ничего не запрашивает в этот момент.

`SnapshotThread.run()` вызывается Qt после `.start()`. Создаёт **собственное** соединение `Database`, вызывает `GameService.snapshot`, посылает результат сигналом `completed`; при исключении посылает сам объект ошибки через `failed`, чтобы GUI отличал `ConnectionLost` от ошибки правил. В `finally` закрывает соединение. `Window.poll` запускает поток, а `Window.apply_snapshot` принимает результат. Передавать уже используемое GUI-соединение в этот поток здесь не требуется.

`ReconnectThread.__init__` сохраняет те же аргументы и поля `database`, `snapshot`, `error`. `run` создаёт новое соединение, получает свежий snapshot либо проверяет доступ к списку комнат, если участия в партии нет. При ошибке закрывает соединение и сохраняет исключение. После успешного восстановления GUI сбрасывает отметки показанных приглашений аукциона и долга: если прежняя команда не выполнилась, актуальный снимок снова предложит решение. При успехе сохраняет соединение для передачи GUI **после сигнала `finished`**, когда поток больше его не использует. Поток не повторяет прерванную игровую команду.

В `app/config.py` нет явно написанных функций: при импорте `load_dotenv()` читает `.env`, а `Settings` — неизменяемая dataclass с параметрами соединения и интервалом опроса. Конструктор создаётся декоратором. По умолчанию `POLL_INTERVAL_MS=2000`, `CONNECT_TIMEOUT_SECONDS=5`, `CALL_TIMEOUT_MS=5000`; `.env` может переопределять значения. Интервал опроса должен быть существенно меньше 60 секунд, а таймауты — положительными. Срок отсутствия игрока задаётся серверной константой `c_disconnect_seconds`, а не локальным таймером интерфейса. `app/main.py` импортирует `main` из интерфейса и запускает её; это не вторая реализация `main`.

### 8.5. Установщик: обе Python-функции и анонимные блоки SQL

`database.install.statements(path: Path)` — генератор команд. Читает файл, пропускает пустые строки, комментарии и известные команды клиента SQL*Plus. Накопитель `buffer` собирает текст, флаг `block` отмечает `BEGIN`, `DECLARE` и определения пакета. Блок выдаёт при отдельном `/`; обычную SQL-команду — после `;`, удаляя завершающую точку с запятой. Выход — последовательность строк через `yield`. Это разбор формата собственных установочных файлов, не универсальный парсер любого Oracle SQL.

`database.install.install(sources=SOURCES, message=...)` — создаёт `Database`, по порядку перебирает переданный список файлов (по умолчанию `SOURCES`), получает команды через `statements` и исполняет их. При ошибке добавляет имя исходного файла в исключение. Затем читает `USER_OBJECTS` и при невалидном пакете получает `USER_ERRORS`; успешное заполнение фиксирует, при исключении вызывает безопасный откат, соединение закрывает в `finally`. Значение не возвращает, печатает результат. **Установка создаёт объекты игры без предварительного удаления. Её запускают один раз в схеме без одноимённых объектов; повторный запуск остановится на ошибке создания уже существующей таблицы. DDL выполняет неявные фиксации, поэтому финальный `ROLLBACK` не отменяет создание объектов.** Для обычного запуска игры установщик не нужен.

В `05_insert_chance_cards.sql` используется анонимный PL/SQL-блок для поиска ID клеток и вставки карт. Он не имеет имени и не сохраняется как отдельная процедура: выполняется при установке. `install.sql` — последовательность команд клиента SQL*Plus, не ещё один пакет.

### 8.6. Обновление существующей базы и проверка связи

После получения нового кода **один раз для общей базы** выполните из корня проекта в активированном окружении:

```bash
python -m database.upgrade
python -m app.main
```

`database.upgrade.upgrade()` передаёт установщику только спецификацию и тело пакета. Команда предназначена для схемы, созданной текущим `02_create_tables.sql`, включая поле `ПОСЛЕДНЯЯ_СВЯЗЬ`: структуру таблиц она не обновляет. Пакет перекомпилируется, затем проверяются `USER_OBJECTS` и `USER_ERRORS`. Пользователи, партии и история сохраняются. Обновлять общий пакет следует между партиями, после чего перезапустить оба клиента. `database.install` предназначен для первой установки.

На новом компьютере нужен Python с зависимостями из `requirements.txt`, доступная Oracle и `.env` с параметрами пользователя схемы. Свежую пустую схему устанавливают через `python -m database.install`; текущие таблицы уже включают новое поле.


Практический сценарий: у одного клиента отключить сеть менее чем на 60 секунд — после восстановления он получает актуальное состояние; затем повторить обрыв дольше 60 секунд при работающем сопернике — оставшийся получает победу. При штатном закрытии ждать 60 секунд не требуется. При пропаже связи окно показывает состояние подключения; восстановление идёт в фоне. Игровые команды пока выполняются в GUI-потоке с ограничением времени обмена, поэтому при первом сетевом сбое возможно краткое ожидание до таймаута.

## 10. Недостатки, ограничения и что действительно стоит упростить

Согласованные правки внесены 18.09.2026. Ниже отделены исправленные случаи и оставшиеся ограничения.

### 10.1. Пустой ID хозяина — исправлено

В `abandon_waiting_game` добавлено `p_user_id IS NULL`. Хозяин может закрыть комнату, другой пользователь и NULL получают ошибку.

### 10.2. Просроченные действия — исправлено

Пример: срок хода истёк в 12:05:00, следующий snapshot придёт в 12:05:02. Бросок в 12:05:01 теперь получит ошибку «Время хода истекло» и не изменит позицию, деньги или журнал. В 12:05:02 snapshot применит предусмотренный правилами тайм-аут и вернёт актуальное состояние.

`require_turn_time` проверяет срок по `SYSDATE` после блокировки строки игры. Его вызывает `require_current_player`, через который проходят бросок, покупка/отказ, улучшение/отказ, продажа построек, покрытие долга и выкуп залога. `end_turn` вызывает проверку после своей блокировки. `make_bid` отдельно проверяет 30-секундный срок аукциона. На точной границе срока действие уже запрещено. Проверка относится к моменту допуска команды после ожидания блокировки.

Проверка команды ничего не меняет и только выдаёт ошибку. Штраф, банкротство и переход хода выполняет `check_game_timer` в транзакции snapshot. Поэтому Python может откатить ошибочную команду, не отменяя обработку тайм-аута. Следующий snapshot фиксирует её отдельно; повторный snapshot не начисляет тот же штраф повторно.

Обработка по опросу сохранена: без клиентов Oracle не выполняет фоновый переход. Это не позволяет сделать просроченный ход — такая команда всё равно будет отклонена. Для применения штрафа и получения нового состояния нужен snapshot.

Аварийное завершение клиента обнаруживается по `ПОСЛЕДНЯЯ_СВЯЗЬ`: `get_game_snapshot` вызывает `heartbeat`, который исключает отсутствующего активного игрока после 60 секунд. Нормальное закрытие пытается отправить `disconnect_player` сразу. Сворачивание не меняет участие. Таймаут связи и двухминутный таймаут хода — разные механизмы; без опрашивающих клиентов проверки откладываются до следующего запроса.

### 10.3. Чат банкрота и выход из игры

Банкрот может читать и писать в чате. Вышедший получает статус `ПОКИНУЛ`: отправка и `get_chat` запрещены, snapshot возвращает пустой чат. Выход активного игрока по-прежнему возвращает имущество банку и учитывается как проигрыш. Выход банкрота также закрывает ему доступ к чату. Завершение партии само по себе не запрещает чат в API; GUI показывает экран результатов.

### 10.4. Ограничения учебной авторизации

Для проекта выбран общий пользователь Oracle и отдельные игровые логины. Учётка удалённого рабочего стола не определяет автоматически пользователя Oracle. Подключение задаётся в `.env` по образцу `.env.example`.

Все клиенты подключаются под одним пользователем Oracle. `authenticate_user` возвращает ID учётной записи, но остальные вызовы принимают ID как обычный аргумент. Поэтому проверка «этот участник сейчас ходит» не доказывает, что соединение принадлежит именно этому человеку. Кроме того, клиентские реквизиты владельца схемы дают возможность напрямую менять таблицы.

У `end_turn` даже нет аргумента участника, только игра. При желании усилить именно эту команду можно добавить ID участника и проверить текущего игрока, но общий вопрос доверия переданным ID этим не решится. Для защиты достаточно честно назвать модель доверенным учебным клиентом; не представлять её как защищённый публичный игровой сервер. Переделка всей системы доступа не нужна для объяснения PL/SQL.

### 10.5. Упрощения — применены

Удалены повторная проверка владельца в `process_cell`, неиспользуемые чтения цветовой группы, ID карты, отдельного уровня в `calculate_rent`, игры/текущего игрока в `leave_active_game`. Убраны недостижимая добровольная ветка `declare_bankruptcy` и неиспользуемая публичная функция `get_board_state`. Поле клиент получает через snapshot.

`get_active_auction` оставлена: её использует `GameService.auction` и обработчик `Window.bid`. Удаление работающего маршрута не является упрощением без изменения возможностей.

Удалён неиспользуемый параметр `Window.poll`. Диалог называется «Покрытие долга», кнопка — «Применить выбранное»; подсказка объясняет продажу уровня. Исправлены переносы PL/SQL. Удаление объектов подавляет только ожидаемые ошибки отсутствия объекта; остальные ошибки передаются вызывающему коду.

Не все дополнительные проверки лишние. Не следует удалять `require_current_player`, проверки этапа/владельца/денег, проверки обоих списков и обработку `NULL` ради короткого кода. Закрытая кнопка в Python не заменяет проверку в Oracle. FK гарантирует существование участника, но не всегда его принадлежность той же игре: поэтому такая проверка в команде имеет самостоятельный смысл.

### 10.6. Что ещё знать при вопросах преподавателя

Дробные ставки запрещены в `make_bid` сравнением с `TRUNC`, в том числе при прямом PL/SQL-вызове. Ноль остаётся отказом от торгов.

Продажа уровня перед броском есть в `sell_buildings`, но в текущем окне управления вне долга показывается только выкуп залога. Это различие между возможностью пакета и возможностью интерфейса; его стоит устранить лишь если такая продажа должна участвовать в демонстрации.

Повтор `set_ready(..., 1)` перезапускает отсчёт готовности. Частичное погашение долга тоже перезапускает свой отсчёт, но второй случай прямо оставлен как правило проекта. Их не надо случайно объявлять одинаковыми ошибками и менять оба без решения о правилах.

Штатные справочные данные существенны для логики: поле жёстко рассчитано на 12 позиций, у покупаемых клеток ожидаются цены, у карт перемещения — подходящие цели. Ограничения не описывают все эти межтабличные правила. Ручное повреждение справочников может нарушить игру; автоматическая проверка всех возможных произвольных наборов справочников сейчас не реализована.

SQL*Plus не требуется: основной запуск установки — `python -m database.install`, который проверяет компиляцию. `database/install.sql` — альтернативный сценарий SQL*Plus. Автоматическую проверку справочников по согласованию не добавляем.

Хэш пароля без соли, отсутствие ограничения попыток входа и доверие ID клиента — ограничения учебной реализации. Для текущей цели полезнее уметь объяснить их, чем добавлять сложную инфраструктуру. Один пакет, существующие справочники и массовый выбор имущества можно сохранить.

### 10.7. Когда считать подготовку законченной

Практический критерий: понятна каждая публичная команда и её внутренний маршрут; исправлена проверка пустого хозяина; согласовано поведение чата; оговорён способ работы таймеров; на нужном компьютере проходит демонстрация входа, покупки, аукциона, долга, банкротства и статистики. После изменения PL/SQL ещё раз проверить `VALID`, отсутствие `USER_ERRORS` и именно затронутые сценарии. Добавлять в проект отдельные пакеты, папку `tests` или файлы миграций ради этой подготовки не требуется.
