# Предложения по оптимизации Monopoly Lite

## Границы анализа

Предложения составлены для текущей архитектуры: один клиент на PySide6 напрямую
подключается к Oracle, игровая логика остаётся в пакете `MONOPOLY`, а интерфейс
периодически получает состояние через `QTimer`. Реализовывать отдельный сервер,
менять правила игры или переносить игровую логику из Oracle не требуется.

Сейчас изменения из этого документа **не реализованы**. Перед каждым этапом нужны
резервная копия схемы, миграция существующих данных и повторный прогон интеграционных
сценариев.

## Что было проанализировано

- `app/main.py`: окна, отрисовка поля, опрос состояния, журнал, чат и действия;
- `app/service.py`, `app/db.py`, `app/config.py`: обращения к пакету Oracle,
  транзакции, преобразование курсоров и частота опроса;
- все SQL-файлы: таблицы, индексы, справочники, представление, пакет и тестовые данные;
- локальные UI-тесты и все сетевые/Oracle-сценарии;
- установка, Windows-скрипт, зависимости и документация запуска.

## Главная причина задержек

Во время активной игры один цикл `Window.poll()` последовательно выполняет:

1. получение состояния игры;
2. проверку таймера с фиксацией транзакции;
3. повторное получение состояния;
4. получение игроков;
5. периодическое получение всего поля;
6. периодическое получение последних 80 событий;
7. периодическое получение всего чата.

При интервале 1,5 секунды два клиента могут создавать десятки отдельных сетевых
обращений к Oracle за минуту даже тогда, когда состояние не изменилось. Интерфейс
ждёт их в GUI-потоке, поэтому задержка базы или сети воспринимается как зависание.

## Рекомендуемый план

### 1. Сократить число обращений к Oracle

Добавить в пакет одну функцию `get_game_snapshot`, возвращающую за один вызов
состояние игры, игроков, изменившиеся владения и новые события. Таймер проверять
внутри этого же вызова. Это заменит 4–7 последовательных обращений одним.

Для сохранения текущей реализации результат можно вернуть несколькими
`SYS_REFCURSOR` или одним JSON/CLOB. Первый вариант проще для существующего
`oracledb` и не требует нового сервера.

Ожидаемый эффект: самое заметное уменьшение лагов при игре через сеть.

### 2. Загружать только изменения

- Передавать в снимок `last_action_id` и получать события только с большим ID,
  а не перечитывать 80 строк.
- Для чата хранить `last_message_id` и запрашивать только новые сообщения.
- Статические сведения клеток загрузить один раз при входе в игру.
- В следующих снимках передавать только владельца, уровень улучшения и залог.
- Полностью перерисовывать поле только при изменении размеров окна; при игровом
  событии обновлять состояние и вызывать одну отложенную перерисовку.

### 3. Не блокировать интерфейс

Вынести сетевой снимок в один рабочий `QThread`/`QThreadPool`. Одновременно может
выполняться только один опрос: если предыдущий ещё идёт, следующий тик пропускается.
Все изменения виджетов должны по-прежнему выполняться только в главном потоке.

После действий пользователя следует немедленный снимок; обычный опрос можно делать
раз в 2 секунды, а цифру таймера между ответами уменьшать локально каждую секунду.

### 4. Разделить крупный файл интерфейса

`app/main.py` содержит более 1500 строк. Без изменения поведения его можно разделить:

- `ui/board.py` — поле и анимация;
- `ui/dialogs.py` — создание комнаты, залог и правила;
- `ui/pages.py` — вход, комнаты, лобби, игра, финал;
- `ui/controller.py` — переходы, снимки состояния и доступность действий;
- `ui/formatters.py` — человекочитаемые события и ошибки.

Это само по себе почти не ускорит игру, но уменьшит риск ошибок и упростит
профилирование и тестирование.

### 5. Упростить данные клеток

В текущих правилах значения вычисляются из цены покупки:

- базовая аренда — 100%;
- аренда с улучшениями — 125%, 150% и 175%;
- каждое улучшение — 25%.

Поэтому после миграции можно удалить из `КЛЕТКИ` поля `БАЗОВАЯ_РЕНТА`,
`РЕНТА_1_ДОМ`, `РЕНТА_2_ДОМА`, `РЕНТА_ОТЕЛЬ` и `ЦЕНА_ДОМА`, вычисляя их в запросе
из `ЦЕНА_ПОКУПКИ`. Это исключит рассинхронизацию цен. Если преподавателю важна
явная структура из ТЗ, поля лучше оставить и добавить проверку согласованности.

`БОНУС_СТАРТА` фактически является глобальной настройкой, а не свойством одной
клетки. Его можно перенести в таблицу `НАСТРОЙКИ_ИГРЫ` или оставить константой
пакета. Для учебного проекта текущий столбец допустим и не влияет на скорость.

### 6. Удалить дублирование и неиспользуемые элементы

Кандидаты требуют проверки требований лабораторной работы:

- `ИГРЫ.ПОСЛЕДНЯЯ_КАРТА_ШАНСА` дублирует последнее событие. Вместо него снимок
  может получать текст карты из журнала, но для этого журналу понадобится поле
  с готовым текстом события либо ссылка на карту.
- Представление `v_game_rooms` сейчас не используется приложением: функцию
  `list_waiting_games` можно перевести на него или удалить представление.
- Методы `request_start`, `kick_participant`, `disconnect_player` и добровольный
  `bankrupt` стоит либо подключить к интерфейсу/сценариям, либо удалить из
  публичной спецификации после подтверждения, что они не требуются ТЗ.
- `Window.update_movements()` сейчас только копирует позиции; его можно удалить,
  поскольку анимация уже хранит позиции внутри `BoardWidget`.

Не следует удалять даты начала/окончания, победителя, очередь хода или журнал:
они нужны завершению игры, статистике и восстановлению состояния.

### 7. Индексы для текущих запросов

После проверки планов выполнения полезны составные индексы:

- `УЧАСТНИКИ(ID_ПОЛЬЗОВАТЕЛЯ, КОД_СТАТУСА_УЧАСТНИКА)`;
- `АУКЦИОНЫ(ID_ИГРЫ, КОД_СТАТУСА_АУКЦИОНА)`;
- `ЖУРНАЛ_ДЕЙСТВИЙ(ID_ИГРЫ, ID_ДЕЙСТВИЯ)`;
- `ЧАТ(ID_УЧАСТНИКА, ID_СООБЩЕНИЯ)` либо денормализованный `ID_ИГРЫ`;
- `ВЛАДЕНИЯ(ID_ВЛАДЕЛЬЦА, ЗАЛОЖЕНА)`.

Индексы нельзя добавлять вслепую: таблицы маленькой учебной игры могут быстрее
обрабатываться без лишних индексов, а каждая запись станет немного дороже.

### 8. Улучшить SQL-пакет без смены логики

- Отформатировать тело пакета: сейчас большие процедуры записаны почти целиком
  в одну строку, что затрудняет поиск ошибок.
- Свести повторные запросы игры участника и клетки к локальным вспомогательным
  функциям или одному исходному `SELECT`.
- Не делать `COUNT(*)`, если требуется только проверка существования; использовать
  выбор одной строки/`EXISTS`.
- Явно блокировать изменяемую игру и участника в одном согласованном порядке,
  чтобы снизить риск взаимных блокировок.
- Добавить версию состояния игры (`STATE_VERSION NUMBER`), увеличиваемую при
  значимом действии. Клиент сможет не загружать поле и журнал, если версия прежняя.

### 9. Тестирование производительности

Добавить сценарий с 2–4 клиентами на 100 ходов, который измеряет:

- среднее и максимальное время снимка;
- число SQL-вызовов на один цикл;
- длительность покупки, аренды и аукциона;
- отсутствие двух одновременных опросов одного клиента;
- стабильность памяти журнала и чата.

Целевые значения для локальной сети: один обычный снимок до 100 мс, действие до
300 мс и не более одного обращения к базе на цикл клиента. Для игры через интернет
важнее именно число сетевых обращений, чем скорость отдельного SQL-запроса.

## Оптимальный порядок внедрения

1. Инкрементальные события/чат и единый снимок.
2. Один фоновый запрос без наложения опросов.
3. Версия состояния и разделение статических/динамических данных поля.
4. Индексы только по результатам измерений.
5. Разделение `main.py`.
6. Удаление дублирующихся столбцов и методов отдельной миграцией.

Первые три пункта дадут основной прирост скорости и сохранят текущую модель:
PySide6-клиент, Oracle и пакет `MONOPOLY`.
